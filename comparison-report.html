Model comparison — cost, time and value per report

Every model was asked the same thing: produce a professional, self-contained HTML report from engine-comparison-summary-data.json. Below is how long each run took and what it cost, read from the finished TUI status bar in each directory's screenshot and cross-checked against the assistant's own usage log — then how good the resulting report was, and what value that represented for the money and time it took.

Report quality

Each generated report was scored 0–100 on how well it does the job of a benchmark report, from checks a machine can repeat. Two different things are on this page: cost and time above measure the run, while quality measures the artifact it produced. They are not the same axis — the dearest run is not the best report.

What this ranking cannot judge

    Return on investment

    ROI here is value per unit of investment, where the value is the report's quality score and the investment is money and time. Quality points are not currency, so rather than invent a dollar figure the analysis asks the only question a buyer can act on: at the quality this run achieved, what was the best deal available? A run's cost is divided by the cheapest run that reached at least its quality, and its time by the fastest such run, giving an efficiency per axis. That alone is not ROI — it is normalised within a quality tier, so a cheap run that scraped a low bar would score as well as a cheap run that produced a strong report. Quality therefore enters again as a multiplier: the score is efficiency scaled by quality relative to the best achieved, so a report at half the best quality can never exceed 50, however little it cost. 100 means the best report at the best available price.

    The value frontier

    The Pareto frontier holds runs that nothing beats on both axes at once. Every expensive run sits inside this frontier: dominated by something cheaper that scored at least as well. The chart marks the union of the cost and time frontiers (), because a run can be the cheapest at its quality or the fastest at it without being both.

    How the ROI score is calculated

    Every figure above is derived from a run's own quality score, cost and time, so the whole calculation can be re-run from comparison-data.json. Nothing is scored by hand and no dollar value is invented for a quality point.

    attainment = quality / best quality of any eligible run (capped at 1) cost_multiple = cost / cheapest run scoring >= this run's quality time_multiple = time / fastest run scoring >= this run's quality cost_efficiency = min(1, 1 / cost_multiple) time_efficiency = min(1, 1 / time_multiple) ROI $ = 100 × attainment × cost_efficiency ROI $+t = 100 × attainment × time_efficiency ROI score = √(ROI $ × ROI $+t) — the headline, and the factor columns are its parts

      The score is capped at 100, quality is this project's rubric rather than a human judgement, and the money figures are one provider's list prices for one run each — not a negotiated rate or a throughput benchmark.

        Method

        Where the numbers come from

        • Time — the Turn N done HH:MM:SS → HH:MM:SS in XmYYs line for each turn, summed across the turns visible in that directory.
        • Cost — the status-bar total for the session. This figure is cumulative, so across several screenshots of one session the largest value is used, never a sum.
        • Usage log — the assistant's own usage.jsonl. Each run was matched to its log entry by the wall-clock overlap of the turn window, not by name or price (directories were renamed after the runs, so their recorded paths no longer match).
        • Quality — each attempt's generated report is opened in headless Chrome by rate_quality.py and scored against the rubric above; the score and the evidence for every check are written to quality-ratings.json. No human judgement is involved and no prose is read.
        • ROI — computed from quality, cost and time by build_comparison.py; the formula and its baselines are set out in the ROI section above. Every figure on this page is reproducible from comparison-data.json.

        Reading the caveats

          What this is not

          • Not an evaluation of the models, only of these reports. Quality is scored by the rubric above and ROI is built from it; neither is a general capability benchmark.
          • Not a controlled experiment. Runs are sequential, on one machine, at one effort level, and the harness changed between attempts, so treat differences as indicative rather than causal.
          • Not exhaustive. Costs come from a single provider's price list at the time of the run.
